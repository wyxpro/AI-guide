# 翠玉AI智能导游系统 · 已有功能完善建议报告 (fx.md)

基于全栈代码库及系统架构的深入剖析，本报告针对“旅行家Pro·景区智能导游系统”的当前实现状态、技术短板、安全机制以及完善方向，提供全方位的诊断与改进建议。

---

## 一、 项目整体架构与实现概述

本项目是一个基于 **Next.js 16 (App Router)**、**React 19**、**Tailwind CSS v4** 以及 **PostgreSQL + Drizzle ORM** 构建的高完成度、响应式双端文旅智能导游系统。
- **游客端 (C端)**：以 HTML5 移动端自适应布局为主，核心亮点在于使用 SVG 矢量技术配合 `framer-motion` 驱动的 AI 数字人交互，支持流式 SSE 问答、打卡、剧情故事导览及偏好设置。
- **管理端 (B端)**：提供给景区运营方使用的中台系统，包括数据大屏、Spots景区景点管理、RAG知识库维护、数字人语音形象配置、情感数据分析及二维码生成生成。
- **AI与网络服务**：采用 `@eazo/sdk` 大模型网关调用 `deepseek.v3.1`，辅以本地基于关键词/标签的文档分发机制，支持 Model Context Protocol (MCP) 智能体协议。

## 三、 后端已有功能完善建议

后端采用 TypeScript 全栈架构设计，数据库层选型为 PostgreSQL 配套 Drizzle ORM，整体性能优异。为提高在高并发 and 文旅实际落地场景中的稳定性，需要完善以下后端设计：

| 模块划分 | 对应文件 / 路由接口 | 现有实现描述 | 存在问题 / 待完善 | 针对性完善建议 |
| :--- | :--- | :--- | :--- | :--- |
| **API 接口层** | `/api/qa/chat` | 接收游客提问，检索景区参考知识库，注入 deepseek.v3.1 进行流式/非流式回答。 | 1. 接口采用“软认证”，允许匿名，容易被脚本恶意刷量；<br>2. 知识库匹配只是用简单的 `question.includes(tag)` 的字符串匹配，非语义化，召回率极低且消耗 Token。 | 1. 引入 IP/用户维度的限流中间件（Rate Limiting），限制频次防御刷量；<br>2. 升级为 Embedding 向量语义召回。 |
| | `/api/user/favorites` | 获取或创建用户的景点/路线收藏。 | Drizzle 在查询用户收藏时，仅返回了 favorites 表的原始 ID 列表，前端不得不二次查询景点信息，多出网络开销。 | 修改后端 API 逻辑，使用 Drizzle 提供的 `leftJoin` 或 `innerJoin` 将 `spots` 与 `routes` 关联，在单次请求中将收藏景点的详情（如图片、名称、评分）合并回传。 |
| | `/api/admin/*` | 管理后台 spots、knowledge、avatar 的操作路由。 | 虽然使用了 `requireAuth` 对登录 Token 进行了校验，但是未验证用户的“角色 (Role)”。非管理员游客如果拦截并发送请求，亦可操作知识库。 | 在 `users` 表或 auth Payload 中增加 `role` 字段（分为 admin / user），在管理员接口中实施严格的 `role === 'admin'` 鉴权过滤，防止越权攻击。 |
| **数据库/数据层**| `schema/user-data.ts` | 定义了 `favorites` 表和 `visit_records` 表。 | 1. `favorites` 表在数据库物理结构上缺少“唯一联合索引 (userId, spotId, routeId)”，极易产生脏数据；<br>2. 缺少商户推荐或优惠券分配的数据承载表。 | 1. 在 `favorites` 的 Drizzle 定义中追加联合唯一约束 `unique("user_spot_route_unique", table.userId, table.spotId, table.routeId)` 并同步迁移；<br>2. 新设商户表与优惠券核销表。 |
| | `schema/admin.ts` | 定义了 `knowledge_docs` 和 `analytics_daily` 表。 | `knowledge_docs` 缺少 `embedding` 字段，无法执行数据库内高效的余弦相似度计算。 | 1. 安装 `pgvector` 扩展；<br>2. 在 `knowledge_docs` 中加入 `embedding: vector("embedding", { dimensions: 1536 })` 字段。 |

## 四、 AI服务功能完善建议

项目采用大模型网关与 MCP 智能体协议，紧跟 AI 技术潮流。但在核心的知识检索（RAG）、多模态交互和智能体（Agent）链路深度上，仍有极大挖掘潜力：

| AI能力模块 | 现有实现方式 | 存在问题与质量瓶颈 | 针对性完善建议 |
| :--- | :--- | :--- | :--- |
| **知识检索 (RAG)** | 对获取到的 6 条知识库文档进行前 4 个字符匹配或标签对比，选取前 3 条作为 Context 拼接。 | 字符截取检索极其粗糙，无法处理同义词、意图理解。若知识库文本极大，粗暴检索会遗漏核心景点介绍，且拼装长文本发往 deepseek 会消耗过多 Token。 | 1. 采用 `OpenAI text-embedding-3-small` 或开源 Embedding 模型将文档转化为向量；<br>2. 游客提问时，先通过向量相似度计算召回最相关的 Top-3 文本片段；<br>3. 引入 Rerank 重排模型，确保最匹配 of 景区指南呈递给大模型。 |
| **多轮对话上下文** | `/api/qa/chat` 获取前端传入的 `history` 数组，截取最后 6 轮送入 LLM。 | 1. 历史记录仅缓存在 C 端网页内存中，一旦游客刷新页面或返回主页，对话上下文全部丢失；<br>2. 历史截取直接用 `slice(-6)`，未过滤系统消息，可能导致角色混淆。 | 1. 每次生成问答时，自动在数据库中 upsert 保存对应的 `chat_sessions`；<br>2. AI 问答端调用 GET 接口能恢复历史对话；<br>3. 确认只保留 role 为 `user` 与 `assistant` 的清洁对话历史送入 LLM。 |
| **多模态与数字人驱动**| 根据前端提问文本，在 client-side 触发 `detectEmotion` 正则判断，切换数字人 SVG 表情。 | 1. 正则规则极为简单，无法正确感知游客语义的细微情感倾向（如赞赏、愤怒、抱怨）；<br>2. 数字人口型只做固定频率（155ms）的二值开合，动作机械，与 TTS 音量大小或文字节奏没有绑定。 | 1. 在后端问答返回时，顺带让大模型输出情感倾向分类（Emotion Output），随流式数据一同下发给前端数字人；<br>2. 前端根据声音响度（Web Audio API analyser）动态决定 SVG 嘴型开合幅度，实现音视频声画同步。 |
| **智能体 MCP 工具链** | 通过 `/api/mcp` 提供了 `list_spots`, `list_routes`, `get_spot` 等静态工具。 | 工具链多为只读（Read-only），智能体（Agent）无法代理用户进行实质性的状态变更操作，如记录足迹或申请收藏。 | 扩展智能体工具集，增加 `add_favorite`、`record_visit_rating`、`book_ticket` 等写操作工具，使 MCP 智能体在第三方平台接入时能真正协助用户游览。 |
